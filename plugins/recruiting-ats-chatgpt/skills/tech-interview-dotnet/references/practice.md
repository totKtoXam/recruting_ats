# Практические задания .NET

Показывай кандидату только условие. Разбор и критерии — для интервьюера.

## Code review (Junior/Middle, 15–20 минут)

Условие: «Это контроллер из нашего проекта. Проведите код-ревью: что здесь не так и как бы вы исправили?»

```csharp
[ApiController]
[Route("api/orders")]
public class OrdersController : ControllerBase
{
    private readonly AppDbContext _db;
    private static List<string> _log = new();

    public OrdersController(AppDbContext db) => _db = db;

    [HttpGet("customer/{customerId}")]
    public List<OrderDto> GetOrders(int customerId)
    {
        var orders = _db.Orders.ToList().Where(o => o.CustomerId == customerId);
        var result = new List<OrderDto>();
        foreach (var order in orders)
        {
            var items = _db.OrderItems.Where(i => i.OrderId == order.Id).ToList();
            result.Add(new OrderDto(order.Id, items.Sum(i => i.Price * i.Quantity)));
        }
        _log.Add($"Orders for {customerId} loaded");
        return result;
    }

    [HttpPost("{id}/notify")]
    public async void Notify(int id)
    {
        var client = new HttpClient();
        var order = _db.Orders.Find(id);
        var response = client.PostAsync("https://notify.example.com", new StringContent(order.Email)).Result;
    }
}
```

Что должен найти (чем больше и чем точнее объяснит — тем выше оценка):
1. `ToList()` до `Where` — вся таблица загружается в память; фильтр должен быть в `IQueryable`.
2. N+1: запрос позиций в цикле — нужна проекция с `Select`/`Include` или `GroupBy` в одном запросе.
3. Синхронный доступ к БД в веб-запросе — лучше `ToListAsync` + `CancellationToken`.
4. `static List` — общий для всех запросов, не потокобезопасен, растёт бесконечно (утечка памяти); для логов — `ILogger`.
5. `async void` в action — исключения не ловятся, ответ уходит до завершения; нужен `async Task<IActionResult>`.
6. `new HttpClient()` на запрос — исчерпание сокетов; `IHttpClientFactory`.
7. `.Result` — блокировка потока; `await`.
8. `Find` может вернуть `null` → `NullReferenceException`; нужен 404.
9. Ответ `PostAsync` не проверяется; нет таймаута и повторов.
10. Бонус: нет авторизации (чужие заказы по `customerId`), `decimal` для денег, пагинация, DTO вместо сущностей.

Оценки для шаблона: `Сильно: нашёл 7+ проблем, объяснил последствия` · `Хорошо: 4–6 проблем` · `Слабо: 1–3 проблемы` · `Не справился`

## Live coding (Middle, 25–30 минут)

### Задача 1. Параллельная загрузка с ограничением
«Есть список из 1000 URL. Скачайте их параллельно, но не больше 10 одновременно, с общим таймаутом 30 секунд и возможностью отмены. Верните словарь URL → размер ответа; ошибки по отдельным URL не должны ронять остальные.»
Ожидаем: `SemaphoreSlim(10)` + `Task.WhenAll` или `Parallel.ForEachAsync` с `MaxDegreeOfParallelism`; `CancellationTokenSource` с таймаутом; `try/catch` на каждый URL; `ConcurrentDictionary` или сбор результатов из задач; один `HttpClient`.
Сильно: корректно, отмена и ошибки обработаны, объясняет выбор. Слабо: `Task.Run` на каждый URL без ограничения, `.Result`.

### Задача 2. LRU-кэш
«Реализуйте кэш на N элементов: `Get(key)` и `Put(key, value)` за O(1); при переполнении вытесняется давно не используемый элемент. Затем — сделайте потокобезопасным.»
Ожидаем: `Dictionary<TKey, LinkedListNode<…>>` + `LinkedList`; перенос в начало при чтении; потокобезопасность — `lock` вокруг операций, обсуждение `ReaderWriterLockSlim` и почему он здесь не помогает (чтение тоже меняет порядок).

### Задача 3 (Junior). Middleware
«Напишите middleware, который добавляет в ответ заголовок `X-Request-Id` (берёт из запроса или генерирует) и пишет в лог метод, путь, статус и время выполнения.»
Ожидаем: класс с `InvokeAsync(HttpContext, RequestDelegate)`, `Stopwatch`, `await next(context)`, `OnStarting` или запись заголовка до отправки ответа, регистрация `app.UseMiddleware<>()`.

## Live coding (Senior, 30 минут)

### Задача 4. Producer/consumer
«Сервис принимает события по HTTP и должен обрабатывать их в фоне пачками по 100 или раз в 2 секунды — что наступит раньше. При остановке приложения необработанные события не должны теряться.»
Ожидаем: `Channel<T>` (bounded, стратегия при переполнении), `BackgroundService`, пакетирование по размеру и таймеру, graceful shutdown через `stoppingToken`, обсуждение надёжности (память процесса vs очередь или outbox в БД).

## System design (Senior, 30–40 минут)

Формат: кандидат задаёт уточняющие вопросы → требования и нагрузка → схема компонентов → данные → узкие места и отказоустойчивость. Оцениваем ход рассуждений, а не «правильную» схему.

### Кейс 1. Приём платежей
«Сервис принимает платежи от клиентов через внешний платёжный шлюз и уведомляет другие сервисы. Нельзя списать дважды и нельзя потерять успешный платёж.»
Сигналы сильного ответа: ключ идемпотентности на входе, состояния платежа (конечный автомат), outbox для событий, повторы с backoff и обработка «не знаем результат» (сверка со шлюзом), аудит, согласованность при сбоях, мониторинг.

### Кейс 2. Уведомления
«Отправка email, SMS и push миллионам пользователей: мгновенные уведомления и массовые рассылки, учёт настроек пользователя, повторы при сбоях провайдера.»
Сигналы: очередь с приоритетами (мгновенные отдельно от рассылок), воркеры по каналам, rate limiting провайдеров, dead letter queue, дедупликация, шаблоны, статусы доставки.

### Кейс 3. Загрузка и обработка файлов
«Пользователи загружают резюме (PDF/DOCX до 10 МБ), система извлекает текст и ищет дубли кандидатов.»
Сигналы: загрузка напрямую в объектное хранилище (presigned URL), асинхронная обработка через очередь, статус обработки, повторы, ограничения размера и типов, антивирус, хранение персональных данных и доступы.

Оценки для шаблона: `Сильно: уточнил требования, компромиссы, отказоустойчивость` · `Хорошо: рабочая схема, слабые места не проработаны` · `Слабо: набор технологий без обоснования` · `Не справился`
