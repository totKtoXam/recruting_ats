# Recruiting ATS

Лёгкая ATS (Applicant Tracking System) на Node.js.

Данные хранятся в PostgreSQL, файлы кандидатов — в Google Drive (как и в прежней версии на Apps Script), пользователи входят через Google.

> Раньше проект работал на Google Apps Script (Google Sheets + Google Drive + clasp). Бэкенд полностью заменён на Node.js 22 + Express 5 + PostgreSQL; резюме по-прежнему лежат в Google Drive с той же структурой папок. Формат RPC сохранён (вместо `google.script.run` фронтенд вызывает `POST /api/rpc/:name`), а интерфейс с тех пор развивается дальше: боковое меню, тёмная тема, архив и корзина, ленты комментариев. Перенос данных из старой таблицы описан в разделе [Миграция из Google Sheets](#миграция-из-google-sheets).

## Возможности

- Kanban по этапам найма с drag & drop, фильтрами и сворачиваемыми колонками.
- Вход через Google OAuth; пользователь идентифицируется по OpenID Connect `sub`.
- Таблица пользователей с автоматическим созданием записи при первом входе и управлением доступом (allowlist email/доменов, переключатель доступа в списке).
- Ответственные — это пользователи с отмеченными этапами найма («Ответственный за этапы»); отдельного справочника ответственных нет. Ответственному не обязателен доступ в ATS (например, интервьюеру, который никогда не входит).
- Разделы вакансий, источников и пользователей; шаблоны интервью ведутся на странице вакансии. Таблицы с фильтрами, сортировкой и пагинацией, которые выполняются на стороне БД.
- Названия вакансий уникальны (без учёта регистра). Статус вакансии меняется кнопками переходов (Открыта → На паузе / Закрыта, На паузе → Открыта / Закрыта, Закрыта → Открыта).
- Единый жизненный цикл для кандидатов, вакансий, источников, шаблонов интервью, результатов интервью и пользователей: активные → архив → корзина (30 дней) → окончательное удаление из БД (см. [Жизненный цикл записей](#жизненный-цикл-записей)).
- Ленты комментариев с ответами, реакциями, редактированием и удалением у кандидатов, вакансий и результатов интервью (см. [Комментарии](#комментарии)).
- Форматированный текст во всех многострочных полях; HTML очищается на сервере по белому списку тегов (см. [Форматированный текст](#форматированный-текст)).
- Главная страница с быстрыми действиями и дашбордами за 7 / 30 / 90 дней (см. [Интерфейс](#интерфейс)).
- Боковое меню, тёмная тема, мгновенные подсказки (см. [Интерфейс](#интерфейс)).
- Карточка кандидата с обязательными ФИО, вакансией, телефоном, рекрутером, ответственным HR, проф. интервьювером и резюме. Рекрутер, HR и проф. интервьювер выбираются из пользователей-ответственных.
- ФЛК мобильного номера Казахстана и email.
- Telegram username автоматически преобразуется в кликабельную ссылку.
- Загрузка PDF/DOC/DOCX резюме (до 10 МБ) в папку кандидата в Google Drive; все версии резюме доступны на странице файлов кандидата, пользователям ATS не нужен собственный доступ к Drive.
- Произвольные дополнительные ссылки кандидата.
- Автозаполнение карточки нового кандидата из файла резюме: кнопка «Заполнить из резюме» или перетаскивание файла в поле «Резюме» (см. [Автозаполнение из резюме](#автозаполнение-из-резюме)).
- Управляемый pipeline: Новый ↔ HR screening ↔ Проф. интервью ↔ Финальное интервью ↔ Offer ↔ Hired, плюс «Отказано» с любого этапа.
- При каждом переходе между этапами открывается форма результата этапа/интервью. Этапы вакансии бывают обязательными: на обязательном этапе без итога переход не сохранится, на необязательном итог можно не указывать. Обязательным можно сделать и этап без шаблона — тогда спрашивается только итог одним текстом.
- Для обязательного шаблона переход блокируется, пока на каждый вопрос не дан ответ или он не отмечен кнопкой «Пропустить» (вопрос не задавался); проверка выполняется и на сервере.
- Каждый переход статуса пишется в append-only таблицу `candidate_status_log` с пользователем, выполнившим переход (UPDATE/DELETE запрещены триггером; исключение — окончательное удаление кандидата из корзины).
- Шаблон вопросов подбирается по вакансии и этапу, **на который** переводят кандидата; у вопросов есть предпочтительные ответы, которые подставляются одним кликом.
- История результатов интервью доступна для просмотра и редактирования; у каждого результата своя лента комментариев.
- Архивирование сохраняет текущий статус кандидата и проставляет `archived_at`; кандидата можно вернуть из архива.
- Resume Intake API для AI-интеграций: создание предзаполненных черновиков кандидатов (см. [`docs/API.md`](docs/API.md)).
- MCP-сервер и плагин Claude Code: Claude работает с ATS от имени пользователя — вход кнопкой «Connect» (OAuth через вход в ATS), превью и подтверждение перед каждым изменением (см. [MCP-сервер и плагин Claude](#mcp-сервер-и-плагин-claude)).
- Swagger UI всего API: `/api/docs`, ссылка — в «Настройки → Для разработчиков» вместе с репозиторием (только после входа; спецификация OpenAPI 3.1 — `/api/openapi.json`, см. [`docs/API.md`](docs/API.md#swagger-ui)).
- Автоматические миграции схемы БД при старте.
- CI в GitHub Actions: тесты, проверка миграций на чистом PostgreSQL, сборка Docker-образа.

## Архитектура

```text
Browser (web/Index.html + Scripts.html)
  |
  |  GET /                 — страница приложения (нужна сессия)
  |  POST /api/rpc/:name   — RPC-методы (JSON, cookie ats.sid)
  |  GET /files/:id        — выдача файла из Google Drive через сервер
  |  /auth/*               — вход через Google / выход
  v
Node.js 22 + Express 5  (server/)
  |-- pg ---------------------> PostgreSQL
  |                               данные ATS + сессии (таблица session)
  |-- @googleapis/drive ------> Google Drive API (папка «Кандидаты»)
  |                               резюме кандидатов и черновиков
  |-- fetch ------------------> Google OAuth 2.0 / OpenID Connect
  ^
  |  GET/POST /intake?api=...  (API key, без сессии)
  |
AI-ассистент / Skill (skills/recruiting-ats-resume)

GitHub --> GitHub Actions (ci.yml)
             npm test
             миграции на postgres:17
             docker build
```

Сервер состоит из одного процесса: HTML, RPC, выдача файлов и Resume Intake API обслуживаются одним Express-приложением.

### Работа фронтенда

Стартовая загрузка ATS использует один RPC `getBootstrapData`. В bootstrap входят:

- текущий пользователь;
- активные вакансии, источники, ответственные (пользователи с этапами), шаблоны и справочники;
- лёгкие карточки активных кандидатов;
- статистика.

Не загружаются при старте:

- архив и корзина кандидатов — загружаются при переключении доски на «Архив» / «Корзина»;
- история интервью — загружается при открытии конкретного кандидата;
- полный объект кандидата с историей резюме и дополнительными ссылками — загружается при открытии карточки;
- ленты комментариев — загружаются при открытии кандидата, вакансии или результата интервью;
- таблицы вакансий, источников и пользователей — загружаются постранично при открытии раздела;
- главная «Мой день» (`getHomeData`: очередь «на моём этапе», кандидаты без движения, вакансии по этапам, последние события) — при открытии «Главной», повторно не чаще раза в минуту;
- «Аналитика» (`getAnalyticsData`: показатели за период, конверсия, источники, причины отказа, нагрузка рекрутеров) — при открытии раздела и смене периода, повторно не чаще раза в минуту;
- полная сводка в прежнем формате (`getDashboardData`) — только для MCP-инструмента `get_dashboard`.

Запись «Последний вход» пользователя обновляется не чаще раза в 30 минут. Тот же `getBootstrapData` в фоне запускает очистку черновиков и окончательное удаление из корзины (см. [Фоновое обслуживание](#фоновое-обслуживание-черновики-и-корзина)).

### Pipeline кандидата

```text
Новый
  ↕
HR screening
  ↕
Проф. интервью
  ↕
Финальное интервью
  ↕
Offer
  ↕
Hired

Любой этап → Отказано → (возврат только на этап, с которого отказали)
```

При переходе на этап заполняется результат этого этапа: вопросы шаблона, назначенного на этап, и ответственный за него (HR — HR screening, проф. интервьювер — Проф. интервью, рекрутер — остальные этапы). Ответы и итог — форматированный текст. Комментарий к переходу становится первым комментарием в ленте созданного результата интервью; в журнал переходов он пишется обычным текстом.

При переводе в «Отказано» указывается, кем отказано (кандидатом или одним из назначенных ему ответственных), и причина из справочника (`dictionaries`, категории «Причины отказа: кандидат» и «Причины отказа: компания»). Для причины «Другое» обязателен комментарий (форматированный текст). Подробности отказа сохраняются в журнале переходов (`candidate_status_log.details`), кандидата можно вернуть на этап, с которого ему отказали.

Переход в архив доступен отдельно из любого активного этапа. Текущий статус кандидата сохраняется, запись остаётся в таблице `candidates` с заполненным `archived_at`; из архива кандидата можно вернуть или (администратору) удалить в корзину — см. [Жизненный цикл записей](#жизненный-цикл-записей).

### Жизненный цикл записей

Кандидаты, вакансии, источники, шаблоны интервью, результаты интервью и пользователи проходят одинаковый путь:

```text
Активные → Архив → Корзина (30 дней) → окончательное удаление из PostgreSQL
              ↑        |
              +--------+  восстановление из корзины (возвращает в архив)
```

- **Архивировать и вернуть из архива** может любой пользователь с доступом; пользователей — только администраторы.
- **Удалить** можно только архивную запись и только администратору. Удалённое попадает в корзину на 30 дней (`TRASH_RETENTION_DAYS` в `server/config.js`); в это время администратор может восстановить запись — она возвращается в архив.
- Через 30 дней запись **физически удаляется из БД** (это не soft delete) вместе с зависимыми данными. У кандидата удаляются результаты интервью, записи о резюме, комментарии и журнал переходов, а папка кандидата в Google Drive переносится в корзину Drive.
- Вакансию, на которую ещё ссылаются кандидаты, и пользователя, назначенного рекрутером / HR / проф. интервьювером у кандидатов, удалить нельзя; если такие ссылки появились, пока запись лежала в корзине, она не удаляется окончательно, пока ссылки не исчезнут.
- Архивный пользователь не может войти и теряет права администратора. Нельзя архивировать самого себя и последнего администратора. После возврата из архива доступ открывается отдельно.
- Окончательное удаление запускается автоматически при открытии приложения (не чаще раза в 12 часов), отдельный cron не нужен.

В интерфейсе у доски кандидатов и у таблиц вакансий, источников и пользователей есть переключатель «Активные / Архив / Корзина»; в корзине у каждой строки показано, сколько дней осталось до окончательного удаления.

### Комментарии

Кандидаты, вакансии и результаты интервью имеют ленту комментариев:

- ответы — один уровень вложенности (ответ на ответ крепится к исходному комментарию);
- у комментария видны автор и относительное время («только что», «5 мин назад», «сегодня в 14:30»), точное время — в подсказке при наведении;
- редактировать может только автор, удалить — автор или администратор (ответы удаляются вместе с комментарием);
- реакции: 👍 👎 ❤️ 😂 🎉 👀.

Комментарий, введённый при создании кандидата (и поле `comment` Resume Intake API), становится первым комментарием в ленте кандидата. У формы вакансии нет отдельного поля комментария — вместо него лента комментариев. Прежние однострочные комментарии кандидатов, вакансий и результатов интервью миграция `004` перенесла в ленты с автором «Перенесено из старой версии» (у результатов интервью — с именем интервьюера, если оно было).

### Уведомления

Колокольчик в верхней панели показывает число непрочитанных и открывает окно с разделами (иконками): **Недавние**, **Непрочитанные**, **Важные** и **Журнал** (переход в «Профиль → Журнал»). Там же «Отметить все как прочитанные». Клик по уведомлению отмечает его прочитанным и открывает карточку кандидата, у уведомления есть и прямая ссылка «Открыть карточку №…» (в колокольчике, журнале и на главной); у каждого уведомления есть кнопки «Детали» (по каким каналам отправлено, статус доставки, адресат, ошибка) и «Важное». Число непрочитанных обновляется раз в 30 секунд.

Виды уведомлений:

| Вид | Когда |
|---|---|
| Назначение карточки | Вас назначили рекрутером, HR или проф. интервьювером кандидата (при создании или переназначении). |
| Изменения в карточке | Любые изменения карточки: поля, резюме, комментарии к кандидату и его интервью, результат интервью, архив и корзина. |
| Перенос карточки | Смена статуса кандидата. |
| Переход на ваш этап | Кандидат перешёл на этап, за который в карточке отвечаете вы (HR screening — HR, Проф. интервью — проф. интервьювер, остальные этапы — рекрутер). |

Получатели — назначенные в карточке и те, кто нажал «Следить» (иконка глаза в шапке карточки). Автор изменения уведомление о своём действии не получает. Каждый получатель получает одно уведомление на событие — самого точного вида, включённого у него в настройках (назначенный HR при переходе на HR screening получит «Переход на ваш этап», а не «Перенос карточки»).

Каналы: **В приложении** (колокольчик), **Эл. почта** (SMTP), **Telegram** (бот). В «Профиль → Уведомления» каждый пользователь включает и выключает любой вид по каждому каналу. По умолчанию включено всё, кроме «Изменений в карточке» по почте и в Telegram. Если выключен канал «В приложении», уведомление не попадает в колокольчик, но остаётся в журнале.

Доставка по почте и в Telegram идёт фоновой очередью (`notification_deliveries`) после сохранения изменения: при ошибке — до 5 попыток с паузами 1, 2, 4, 8 минут; если канал не настроен или у пользователя нет адреса, доставка помечается «Не отправлено» с причиной. Уведомления старше 180 дней, кроме отмеченных важными, удаляются автоматически.

### Telegram

У пользователя есть поле Telegram. Администратор может вписать ник в форме пользователя, но такой ник считается **неподтверждённым**: боту по нику писать нельзя, и владение аккаунтом не проверено. Подтверждение делает сам пользователь:

1. «Профиль → Уведомления → Привязать Telegram» — сервер выдаёт одноразовый код на 15 минут и открывает ссылку `https://t.me/<бот>?start=<код>`.
2. Пользователь нажимает «Старт» в боте — Telegram присылает боту `/start <код>` от имени именно этого аккаунта.
3. Сервер сохраняет `chat_id` и `@username` из Telegram — аккаунт подтверждён (в списке пользователей рядом с ником появляется ✓), уведомления приходят в этот чат.

Отвязать можно в настройках или командой `/stop` в боте. Если администратор меняет ник, подтверждение сбрасывается. Бот получает сообщения long polling-ом (`getUpdates`) — вебхук и публичный HTTPS-адрес не нужны, работает и локально. Если экземпляров приложения несколько, `TELEGRAM_POLLING=true` оставьте только на одном.

Создание бота: в Telegram откройте `@BotFather` → `/newbot`, задайте имя и username бота, скопируйте токен в `TELEGRAM_BOT_TOKEN` и перезапустите сервер (в логе: «Telegram: бот @… подключён»).

### Интеграции (настройки администратора)

«Настройки → Интеграции» (только администраторы) — вход через Google, SMTP и Telegram-бот без правки `.env` и без перезапуска:

| Группа | Поля |
|---|---|
| Вход через Google | Client ID, Client secret, домены и email с автоматическим доступом |
| Эл. почта (SMTP) | сервер, порт, TLS, логин, пароль, отправитель |
| Telegram-бот | токен, приём сообщений (long polling) |

- Значение из интерфейса важнее переменной окружения; у каждого поля видно, откуда оно: «задано в ATS», «из .env», «по умолчанию», «не задано». Сохраняются только изменённые поля.
- «Сбросить к .env» удаляет сохранённые в ATS значения группы.
- «Проверить»: для Google — проверка Client ID и secret в Google (обмен заведомо неверного кода: `invalid_grant` — клиент настоящий, `invalid_client` — нет); для SMTP — подключение и тестовое письмо на ваш email; для Telegram — `getMe` с токеном. Проверяются и ещё не сохранённые значения.
- Client ID и secret проверяются в Google и при сохранении: неверные не сохранятся, чтобы никто не потерял вход. В карточке показаны Redirect URI и JS origin для Google Cloud Console.
- Секреты (пароль SMTP, токен бота, Client secret) хранятся в `app_settings` зашифрованными (AES-256-GCM, ключ из `SETTINGS_ENCRYPTION_KEY`, иначе из `SESSION_SECRET`) и не отдаются в браузер — видны только последние 4 символа. Пустое поле секрета при сохранении означает «не менять». Если ключ сменился, сохранённый секрет помечается «не расшифровано» и действует значение из `.env`.
- Не меняются в интерфейсе: `AUTH_MODE`, `AUTH_ADMIN_EMAILS` (постоянные администраторы — страховка от потери доступа), `PUBLIC_URL`, Google Drive (у Drive свой OAuth-клиент и refresh token из `.env`).
- Если вход всё же сломан, на сервере: `npm run settings:reset -- auth` (или без аргумента — все группы), затем перезапуск.

### Автозаполнение из резюме

В форме нового кандидата резюме можно не только приложить, но и разобрать: кнопка «Заполнить из резюме» (с подсказкой при открытии формы) или перетаскивание файла в поле «Резюме». Файл разбирает сервер (`parseResume`), ничего не сохраняя; тот же файл остаётся выбранным как резюме кандидата.

- **Форматы файла** — PDF (`unpdf`), DOCX (`mammoth`), DOC (`word-extractor`). Текст собирается по координатам, поэтому двухколоночные макеты не склеиваются; ссылки берутся и из аннотаций PDF / гиперссылок DOCX — часто адрес есть только там. Сканы без текстового слоя и распечатки вакансий hh отклоняются с пояснением.
- **Шаблоны.** Резюме с hh.ru/hh.kz распознаётся по подвалу «Резюме обновлено …» и разбирается детерминированно: ФИО (отчество — по разнице заголовка и подвала «Фамилия Имя»), контакты, мессенджеры, желаемая должность и зарплата, а также служебные блоки работодателя: отклик на вакансию, отказы, комментарии рекрутера, сопроводительное письмо. Выгрузка enbek.kz — по заголовкам разделов. Остальное — свободная форма: контакты регулярными выражениями, ФИО по крупному шрифту в шапке + словарь имён (`server/lib/person-names.js`) и суффиксы фамилий/отчеств.
- **Принцип: лучше пусто, чем неверно.** Значение подставляется только в пустое поле и только если оно прошло те же проверки, что и форма (`normalizeKzPhone`, `validateEmail`, `normalizeTelegram`, `normalizeProfileUrl`). Неуверенные значения (порядок «Фамилия Имя» у незнакомых имён, телефон не РК, email с необычным доменом, второй адрес) показываются в панели кнопкой «Подставить». Подставленные поля помечены цветом (синий — уверенно, жёлтый — проверьте); отметка снимается при правке, «Отменить» возвращает всё как было.
- **Подсказки по справочникам.** Вакансия подставляется при точном совпадении с откликом в hh или желаемой должностью, иначе предлагается похожая; источник — по формату резюме (hh, enbek, LinkedIn), если такой есть в справочнике. Ссылки на профили (hh, GitLab, Stack Overflow, HackerRank, Behance…) добавляются в «Иные ссылки»; сертификаты и сайты работодателей не берутся.
- **Дубли.** Пока заполняется новая карточка, под полями ФИО показываются похожие кандидаты (см. [Похожие кандидаты](#похожие-кандидаты)); после автозаполнения проверка запускается сразу.
- **В комментарий.** Краткая выжимка (город, возраст, опыт, формат работы, дата обновления резюме) и блоки hh (отклик, отказ, комментарий рекрутера, сопроводительное письмо) добавляются в первый комментарий одной кнопкой; автоматически комментарий не заполняется.
- **Точность на эталонном наборе** (21 реальное резюме: 11 hh, 1 enbek, 9 в свободной форме): ФИО, телефон, email, Telegram, GitHub и LinkedIn — без ошибок, у одного резюме порядок имени подтверждён по email с пометкой «проверьте». Зарплату в выборке никто не указал. Набор лежит в `test/fixtures/resumes/` (в `.gitignore` — персональные данные) и проверяется тестом `test/resume-parse.test.js`, если папка есть.

### Похожие кандидаты

Чтобы не завести дубль, форма нового кандидата по мере ввода (с задержкой 400 мс) спрашивает сервер (`findSimilarCandidates`) и показывает под полями ФИО до пяти похожих кандидатов, включая архив и корзину, со ссылкой на карточку и причиной: «тот же email / телефон / Telegram» (точное совпадение, красный блок) или «похожее ФИО (92 %)» (жёлтый).

ФИО сравниваются расстоянием Дамерау — Левенштейна по «скелету» имени (`server/lib/person-names.js`): регистр, лишние пробелы, ё/е, дефисы, латиница и кириллица, варианты транслитерации различием не считаются, а опечатка или перестановка соседних букв стоит одну правку. Порог сходства — 0,8 по фамилии и имени (порядок «Фамилия Имя» может быть перепутан — сравнивается и крест-накрест); по одной фамилии — от 4 символов, по одному имени — от 0,9. Разные отчества при похожих фамилии и имени снижают оценку. Поиск не блокирует сохранение — это предупреждение.
Все многострочные поля — редакторы форматированного текста: жирный, курсив, подчёркивание, зачёркивание, списки, цитата, код, ссылки. Текст хранится как HTML и очищается на сервере библиотекой `sanitize-html` (`server/lib/richtext.js`) по белому списку тегов: `p`, `br`, `strong`, `em`, `u`, `s`, `ul`, `ol`, `li`, `a` (только `http`, `https`, `mailto`; открываются в новой вкладке с `rel="noopener noreferrer"`), `blockquote`, `code`. Всё остальное отбрасывается.

HTML хранят ответы на вопросы интервью, итог интервью, комментарий к отказу и комментарии. Журнал переходов (`candidate_status_log`) по-прежнему хранит обычный текст. Если клиент присылает обычный текст (например, Resume Intake API), сервер экранирует его и превращает в HTML.

### Интерфейс

- **Главная** (`#/home`, открывается при входе) — быстрые действия (новый кандидат, заполнение из резюме, вакансия, источник, пользователь, доска, архив, уведомления, интеграции, профиль) и дашборды за 7 / 30 / 90 дней: ключевые показатели с дельтой к предыдущему периоду (новые, офферы, наймы, отказы, среднее время найма), воронка по этапам, график новых кандидатов (по дням или неделям, с таблицей), «На моём этапе» (кандидаты, где вы отвечаете за текущий этап), «Без движения» (дольше 14 дней на этапе), вакансии, источники, причины отказа, нагрузка рекрутеров, недавние кандидаты, последние события из журнала изменений и непрочитанные уведомления. Карточки кандидатов открываются поверх главной; период запоминается в `localStorage` (`ats:home-period`).
- Слева — боковое меню: **Главная**, сворачиваемая группа **Рекрутинг** (Кандидаты, Вакансии) и **Настройки** (Источники вакансий, Пользователи, Интеграции). Разделы «Пользователи» и «Интеграции» видны только администраторам. Само меню тоже сворачивается.
- Кнопки действий форм и модальных окон расположены вверху.
- Всё личное — в меню под именем пользователя в верхней панели: «Профиль» (аккаунт, оформление), «Уведомления» (подписки, Telegram), «Журнал уведомлений», переключатель темы и «Выйти». Страница профиля — `#/profile`, `#/profile/notifications`, `#/profile/log`; прежние адреса `#/settings/notifications…` перенаправляются туда.
- Тема: «как в системе», светлая или тёмная (`ThemeManager` в `web/UiKit.html`), выбор хранится в `localStorage` под ключом `ats:theme`.
- Формы справочников (вакансии, источники, пользователи) открываются в выдвижной панели справа по клику на строку или «+».
- Подсказки у кнопок (атрибут `data-tip`) появляются сразу, без задержки браузерного `title`.

## Требования

- Node.js 22+ и npm.
- PostgreSQL 14+ (в разработке и CI используется 17).
- Docker и Docker Compose — для локальной разработки и деплоя (рекомендуется).
- Google Cloud проект с OAuth client — для входа через Google и доступа к Google Drive (включённый Google Drive API).
- Папка в Google Drive для резюме (обычного бесплатного Gmail достаточно) — см. [Настройка Google Drive](#настройка-google-drive).

## Быстрый старт (локально)

```bash
cp .env.example .env
```

Сгенерируй `SESSION_SECRET` и впиши его в `.env`:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
```

Подними PostgreSQL:

```bash
docker compose up -d postgres
```

Настрой доступ к Google Drive и впиши `GOOGLE_DRIVE_ROOT_FOLDER_ID` и `GOOGLE_DRIVE_REFRESH_TOKEN` в `.env` — см. [Настройка Google Drive](#настройка-google-drive). Без этого сервер не стартует.

Установи зависимости и запусти сервер в режиме разработки:

```bash
npm install
npm run dev
```

Открой http://localhost:3040.

В `.env.example` по умолчанию стоит `AUTH_MODE=dev` — вход по email без пароля. Пока allowlist не задан, доступ автоматически получает только первый вошедший пользователь. Для проверки входа через Google см. [Настройка Google OAuth](#настройка-google-oauth).

При старте сервер сам:

- накатывает миграции БД (под advisory lock, поэтому безопасно при нескольких инстансах);
- проверяет доступ к корневой папке Google Drive (`GOOGLE_DRIVE_ROOT_FOLDER_ID`) и при ошибке сразу завершается с понятным сообщением.

### Полный стек в Docker

```bash
docker compose --profile app up --build
```

В `docker-compose.yml` только PostgreSQL и приложение (профиль `app`). Контейнер `app` берёт переменные из `.env`, а `DATABASE_URL` переопределяет на адрес PostgreSQL внутри compose-сети. Файлы хранятся в Google Drive, отдельное хранилище поднимать не нужно.

### Тесты

```bash
npm test
```

Unit-тесты на `node:test` лежат в `test/`.

Тест разбора резюме дополнительно прогоняет эталонный набор реальных резюме из `test/fixtures/resumes/` (папка в `.gitignore`, в репозитории её нет): положите туда файлы и `expected.json` вида `{ "file.pdf": { "status": "ok", "format": "hh", "fields": { "lastName": "…" } } }`. Без папки тест пропускается.

## Настройка Google OAuth

1. Открой [Google Cloud Console](https://console.cloud.google.com/) и выбери или создай проект.
2. `APIs & Services -> OAuth consent screen` — настрой экран согласия. Для корпоративного Google Workspace удобно выбрать тип `Internal`: тогда войти смогут только аккаунты домена.
3. `APIs & Services -> Credentials -> Create credentials -> OAuth client ID`.
4. Тип приложения — **Web application**.
5. В `Authorized redirect URIs` добавь:

   ```text
   <PUBLIC_URL>/auth/google/callback
   ```

   Например, `https://ats.example.com/auth/google/callback`, а для локальной проверки — `http://localhost:3040/auth/google/callback`.

6. Скопируй Client ID и Client secret в `GOOGLE_CLIENT_ID` и `GOOGLE_CLIENT_SECRET`, установи `AUTH_MODE=google`.

Приложение запрашивает только scope `openid email profile`. Вход с неподтверждённым email Google отклоняется.

> `PUBLIC_URL` должен в точности совпадать с адресом, по которому пользователи открывают ATS, иначе Google вернёт `redirect_uri_mismatch`.

## Настройка Google Drive

Резюме хранятся в Google Drive. Приложение работает с Drive от имени одного аккаунта (режим `oauth`) или сервисного аккаунта (режим `service_account`) и отдаёт файлы пользователям через себя — самим пользователям ATS доступ к папке в Drive не нужен.

### Режим `oauth` (по умолчанию)

Приложение действует от имени одного Google-аккаунта — так же, как Apps Script с «Execute as: Me». Подходит обычный бесплатный Gmail; файлы занимают квоту этого аккаунта (15 ГБ у бесплатного).

1. Создай в Drive этого аккаунта папку «Кандидаты» (или используй старую, см. [Миграция из Google Sheets](#миграция-из-google-sheets)) и скопируй её ID из адреса `https://drive.google.com/drive/folders/<ID>` в `GOOGLE_DRIVE_ROOT_FOLDER_ID`.
2. В том же Google Cloud проекте включи **Google Drive API**: `APIs & Services -> Library -> Google Drive API -> Enable`.
3. В OAuth-клиенте из [Настройки Google OAuth](#настройка-google-oauth) добавь в `Authorized redirect URIs`:

   ```text
   http://localhost:53682/oauth2callback
   ```

   Отдельный OAuth-клиент для Drive не обязателен: по умолчанию берутся `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` (их можно переопределить через `GOOGLE_DRIVE_CLIENT_ID` / `GOOGLE_DRIVE_CLIENT_SECRET`).
4. Запусти:

   ```bash
   npm run drive:auth
   ```

   Открой выведенную ссылку, войди аккаунтом-владельцем папки и разреши доступ.
5. Скопируй выведенный refresh token в `GOOGLE_DRIVE_REFRESH_TOKEN`, `GOOGLE_DRIVE_AUTH=oauth`.

Запрашивается scope `https://www.googleapis.com/auth/drive`.

> **Важно.** Если экран согласия OAuth в статусе публикации **Testing**, refresh token истекает через 7 дней, и загрузка резюме перестанет работать. Переведи экран согласия в **In production** (`APIs & Services -> OAuth consent screen -> Publish app`). Для личного/внутреннего использования верификация приложения не нужна: неверифицированное приложение работает, пользователь один раз видит экран-предупреждение. В Google Workspace можно вместо этого выбрать тип `Internal`.

### Режим `service_account`

Работает **только с общим диском (Shared Drive) Google Workspace**: у сервисного аккаунта нет собственной квоты хранилища, поэтому в обычный «Мой диск» он загружать файлы не может.

1. Создай сервисный аккаунт в Google Cloud, включи Google Drive API и выпусти JSON-ключ.
2. Добавь email сервисного аккаунта участником общего диска с ролью **Content manager** («Менеджер контента»).
3. Создай на общем диске папку «Кандидаты» и укажи её ID в `GOOGLE_DRIVE_ROOT_FOLDER_ID`.
4. Установи `GOOGLE_DRIVE_AUTH=service_account` и передай ключ в `GOOGLE_DRIVE_SERVICE_ACCOUNT_KEY` (JSON одной строкой) или путь к файлу ключа в `GOOGLE_APPLICATION_CREDENTIALS`.

### Проверка при старте

При старте сервер проверяет, что `GOOGLE_DRIVE_ROOT_FOLDER_ID` задан, указывает на папку не в корзине и доступен аккаунту приложения. Иначе сервер не запускается и пишет в лог причину (например, «Папка GOOGLE_DRIVE_ROOT_FOLDER_ID не найдена или у аккаунта приложения нет к ней доступа»).

## Управление доступом

Войти через Google может **любой аккаунт любого домена**, но работать в ATS — только тот, кому администратор открыл доступ. Доступ управляется в интерфейсе: **Настройки → Пользователи** (раздел виден только администраторам, права проверяются на сервере).

- **Администраторы** из `AUTH_ADMIN_EMAILS` всегда имеют доступ и права администратора — с них начинается работа (даже архивный пользователь из этого списка при входе возвращается из архива). Других администраторов можно назначить в интерфейсе.
- **Добавить пользователя заранее:** «+» → Фамилия, Имя, Отчество, email его Google Account, при необходимости этапы «Ответственный за этапы» и флажок «Открыть доступ в ATS» (флажок есть только при создании). Email обязателен всегда, даже для ответственного без доступа. После первого входа подтянется аватар из Google; ФИО заполняется из Google (`given_name` / `family_name`) только если оно пустое — ФИО, введённое администратором, не перезаписывается.
- **Email** можно исправить, пока человек ни разу не входил через Google (например, заменить временный адрес).
- **Ответственные:** пользователь с хотя бы одним отмеченным этапом в «Ответственный за этапы» — ответственный: его можно назначить рекрутером (все этапы), HR или проф. интервьювером кандидата. Доступ в ATS для этого не нужен — например, интервьюер может никогда не входить в систему.
- **Кто пытался войти без доступа**, попадает в список со статусом «Ожидает доступа» (сортировка по умолчанию показывает их первыми).
- **Открыть / закрыть доступ** — переключателем «Доступ» в строке таблицы пользователей. Пользователь разлогинивается при следующем запросе: сессия проверяется на каждом запросе. Права администратора подразумевают доступ.
- **Архив и корзина пользователей** — только для администраторов; архивный пользователь не может войти и теряет права администратора (см. [Жизненный цикл записей](#жизненный-цикл-записей)).
- Нельзя закрыть доступ, снять права администратора или архивировать самого себя, а также снять права с последнего администратора или архивировать его.
- Необязательно: `AUTH_ALLOWED_EMAILS` / `AUTH_ALLOWED_DOMAINS` открывают доступ автоматически (без прав администратора).
- Без `AUTH_ADMIN_EMAILS` и allowlist (только вне production) доступ и права администратора получает самый первый вошедший пользователь. В `NODE_ENV=production` сервер без `AUTH_ADMIN_EMAILS` не стартует.

Чтобы входить могли аккаунты любых доменов, OAuth-клиент в Google Cloud должен быть типа **External** и опубликован (**Publish app**, статус «In production»). Для входа приложение запрашивает только email и профиль, поэтому проверка приложения Google не требуется. Тип **Internal** пускает только аккаунты вашей организации Google Workspace.

Остальные разделы (кандидаты, вакансии, источники) доступны всем пользователям с доступом; удаление в корзину и восстановление из неё — только администраторам.

### Перенос ответственных (миграция `004`)

Раньше ответственные были отдельным справочником. Миграция `004_users_lifecycle_comments.sql` объединила их с пользователями:

- ответственный, привязанный к пользователю (или совпадающий с ним по email), слился с этим пользователем: ФИО и этапы взяты из карточки ответственного;
- остальные ответственные стали пользователями **без доступа** в ATS;
- у кого не было email, получил временный адрес `responsible-<№>@no-email.invalid` — администратору нужно заменить его настоящим email в «Настройки → Пользователи» (это возможно, пока человек не входил);
- назначения кандидатов (рекрутер, HR, проф. интервьювер), ответственные в результатах интервью и в журнале переходов теперь ссылаются на пользователей.

Подключиться к БД в локальном compose:

```bash
docker compose exec postgres psql -U ats -d ats
```

## Deploy

### Render (бесплатно, без карты)

В репозитории есть Blueprint [`render.yaml`](render.yaml): Node-сервис на бесплатном тарифе Render, деплой при каждом push в `main`. Банковская карта не нужна. Бесплатный сервис засыпает через ~15 минут без запросов, и первое открытие после сна занимает 30–60 секунд.

1. **PostgreSQL** — создай бесплатную базу на [Neon](https://neon.tech) (регион Frankfurt, ближе к Render) и скопируй connection string вида `postgres://…neon.tech/…?sslmode=require`. Бесплатная база самого Render удаляется через 30 дней, поэтому она не подходит.
2. **Google Cloud Console** — проект с OAuth-клиентом для входа и включённым Google Drive API (см. [Настройка Google OAuth](#настройка-google-oauth) и [Настройка Google Drive](#настройка-google-drive)). Billing-аккаунт и карта для этого не нужны. Refresh token для Drive получи локально: `npm run drive:auth`.
3. **Сервис** — Render → **New → Blueprint** → выбери этот репозиторий. Render создаст сервис `recruiting-ats`; `SESSION_SECRET` и `ATS_API_KEY` сгенерируются автоматически.
4. **Переменные** (Render спросит их при создании, позже — Service → Environment):
   - `PUBLIC_URL` — `https://recruiting-ats.onrender.com` (точный адрес виден в дашборде);
   - `DATABASE_URL` — строка подключения Neon;
   - `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`;
   - `AUTH_ALLOWED_DOMAINS` и/или `AUTH_ALLOWED_EMAILS` — без них сервер в production не стартует;
   - `GOOGLE_DRIVE_ROOT_FOLDER_ID`, `GOOGLE_DRIVE_REFRESH_TOKEN`.
5. В OAuth-клиенте добавь Authorized redirect URI `https://<адрес>.onrender.com/auth/google/callback`.

Схема БД создаётся автоматически при первом старте. Если нужно перенести данные из старой таблицы, выполни импорт локально, указав `DATABASE_URL` базы Neon (см. [Миграция из Google Sheets](#миграция-из-google-sheets)).

### Google Cloud Run (альтернатива, нужна карта)

Cloud Run запускает контейнер из `Dockerfile` и останавливает его, когда нет запросов. Бесплатно ежемесячно: около 2 млн запросов, 180 000 vCPU-секунд и 360 000 GiB-секунд — для небольшой команды рекрутеров этого с запасом хватает. Холодный старт после простоя занимает несколько секунд. Лимит запроса — 32 МБ, так что резюме до 10 МБ проходят. Актуальные условия: https://cloud.google.com/free.

База — бесплатный PostgreSQL на [Neon](https://neon.tech): у Cloud SQL бесплатного тарифа нет.

**Один раз (в консоли Google Cloud и Neon):**

1. Создай проект в [Google Cloud Console](https://console.cloud.google.com) (тот же, где OAuth-клиент для входа и Google Drive API) и подключи к нему billing-аккаунт. Карта нужна, даже если укладываться в бесплатный лимит; в некоторых странах при создании billing-аккаунта Google требует предоплату или временно блокирует сумму на карте. Сразу настрой бюджет с оповещением (**Billing → Budgets & alerts**, например $1).
2. Создай базу на Neon (регион Frankfurt, ближе к `europe-west1`) и скопируй connection string `postgres://…neon.tech/…?sslmode=require`.
3. Получи refresh token для Drive: `npm run drive:auth` (см. [Настройка Google Drive](#настройка-google-drive)).
4. Установи [Google Cloud CLI](https://cloud.google.com/sdk/docs/install) и выполни `gcloud auth login`. Вместо установки можно работать в [Cloud Shell](https://shell.cloud.google.com) — там `gcloud` уже есть, достаточно склонировать репозиторий.

**Деплой:**

1. Скопируй `.env.example` в `.env.cloudrun` (файл не попадает в git) и заполни:
   - `DATABASE_URL` — строка подключения Neon;
   - `SESSION_SECRET`, `ATS_API_KEY` — случайные строки (команды генерации есть в `.env.example`);
   - `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`;
   - `AUTH_ALLOWED_DOMAINS` и/или `AUTH_ALLOWED_EMAILS` — без них сервер в production не стартует;
   - `GOOGLE_DRIVE_ROOT_FOLDER_ID`, `GOOGLE_DRIVE_REFRESH_TOKEN`;
   - `PUBLIC_URL` можно не задавать — скрипт вычислит адрес сервиса `https://recruiting-ats-<номер проекта>.europe-west1.run.app`.
2. Запусти:

   ```bash
   PROJECT_ID=<id-проекта> ./scripts/deploy-cloud-run.sh
   ```

   Скрипт включает нужные API, создаёт сервисный аккаунт сервиса, кладёт `SESSION_SECRET`, `DATABASE_URL`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_DRIVE_REFRESH_TOKEN` и `ATS_API_KEY` в Secret Manager (5 секретов укладываются в бесплатный лимит), собирает образ в Cloud Build и выкатывает сервис (`min-instances=0`, `max-instances=2` — защита от неожиданных расходов). Регион и имя меняются переменными `REGION` и `SERVICE`.
3. В OAuth-клиенте добавь Authorized redirect URI `https://<адрес-сервиса>/auth/google/callback` — скрипт выводит его в конце.

Схема БД создаётся автоматически при первом старте. Повторный запуск скрипта выкатывает новую версию из текущей рабочей копии и обновляет только изменившиеся секреты. Для автодеплоя при push в `main` можно в консоли открыть сервис Cloud Run → **Set up continuous deployment** и подключить GitHub-репозиторий: переменные и секреты сервиса сохранятся.

Если нужно перенести данные из старой таблицы, выполни импорт локально, указав `DATABASE_URL` базы Neon (см. [Миграция из Google Sheets](#миграция-из-google-sheets)).

### Docker-образ

`Dockerfile` собирает production-образ на `node:22-alpine`: только production-зависимости, запуск от пользователя `node`, порт `3040`, healthcheck на `GET /healthz`.

```bash
docker build -t recruiting-ats .
docker run -d --name recruiting-ats \
  --env-file .env.production \
  -p 3040:3040 \
  recruiting-ats
```

Минимальный набор переменных для production:

```dotenv
NODE_ENV=production
PUBLIC_URL=https://ats.example.com
TRUST_PROXY=true
DATABASE_URL=postgres://...
SESSION_SECRET=<не короче 32 символов>
AUTH_MODE=google
GOOGLE_CLIENT_ID=...
GOOGLE_CLIENT_SECRET=...
AUTH_ALLOWED_DOMAINS=example.com
GOOGLE_DRIVE_ROOT_FOLDER_ID=...
GOOGLE_DRIVE_AUTH=oauth
GOOGLE_DRIVE_REFRESH_TOKEN=...
ATS_API_KEY=...
```

При `NODE_ENV=production` сервер не стартует, если `SESSION_SECRET` короче 32 символов, включён `AUTH_MODE=dev` или не заданы `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`, пуст allowlist (`AUTH_ALLOWED_DOMAINS` / `AUTH_ALLOWED_EMAILS`) или задан тестовый `GOOGLE_DRIVE_API_URL`. В любом окружении сервер не стартует без доступа к папке Google Drive.

Для хранения файлов отдельное объектное хранилище не нужно: достаточно PostgreSQL и Google Drive, что упрощает бесплатный или дешёвый хостинг.

Миграции применяются автоматически при старте контейнера. Их можно запустить и отдельно:

```bash
npm run migrate
```

`GET /healthz` возвращает `{"ok":true}`, если приложение доступно и отвечает БД, иначе `503`.

### Reverse proxy и HTTPS

В production приложение должно работать только по HTTPS: cookie сессии `ats.sid` выставляется с флагом `Secure`.

Обычно TLS терминируется на reverse proxy (nginx, Caddy, Traefik, облачный load balancer). В этом случае:

- установи `TRUST_PROXY=true` — Express будет доверять `X-Forwarded-Proto` от первого прокси; без этого secure cookie не выставится и вход будет «зацикливаться»;
- прокси должен передавать заголовки `Host` и `X-Forwarded-Proto`;
- лимит тела запроса на прокси — не меньше 20 МБ (резюме передаются в base64 внутри JSON);
- для MCP-клиентов прокси должен пропускать `{BASE_PATH}/mcp`, `{BASE_PATH}/oauth/*` и `{BASE_PATH}/.well-known/*` и, если приложение открыто под `BASE_PATH`, три корневых адреса метаданных OAuth — Claude Code ищет их в корне домена (иначе вход обрывается на регистрации клиента с 404):

```nginx
location = /.well-known/oauth-protected-resource/hr-ats/mcp  { proxy_pass http://127.0.0.1:3040; proxy_set_header Host $host; proxy_set_header X-Forwarded-Proto https; }
location = /.well-known/oauth-authorization-server/hr-ats    { proxy_pass http://127.0.0.1:3040; proxy_set_header Host $host; proxy_set_header X-Forwarded-Proto https; }
location = /.well-known/openid-configuration/hr-ats          { proxy_pass http://127.0.0.1:3040; proxy_set_header Host $host; proxy_set_header X-Forwarded-Proto https; }
```

  (`/hr-ats` — ваш `BASE_PATH`).

Пример для nginx:

```nginx
server {
    listen 443 ssl;
    server_name ats.example.com;

    client_max_body_size 20m;

    location / {
        proxy_pass http://127.0.0.1:3040;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

Не публикуй порт `3040` напрямую в интернет — только через прокси.

### Фоновое обслуживание: черновики и корзина

Сервер сам выполняет две фоновые задачи. Обе запускаются при открытии приложения (`getBootstrapData`), каждая не чаще раза в 12 часов. Таймеры и отдельный cron не используются: на Cloud Run и других serverless-хостингах процесс между запросами почти не получает CPU.

- **Очистка черновиков** — удаляет использованные и просроченные черновики Resume Intake API; их файлы переносятся в корзину Google Drive, а не удаляются безвозвратно.
- **Окончательное удаление из корзины** — записи, пролежавшие в корзине ATS больше 30 дней, удаляются из PostgreSQL вместе с зависимыми данными; папки удалённых кандидатов переносятся в корзину Google Drive (см. [Жизненный цикл записей](#жизненный-цикл-записей)).

Запустить очистку черновиков вручную:

```bash
npm run cleanup-drafts
```

## Миграция из Google Sheets

Скрипт `scripts/import-from-xlsx.js` переносит данные из прежней Google-таблицы Recruiting ATS в PostgreSQL.

1. Настрой Google Drive (см. [Настройка Google Drive](#настройка-google-drive)): укажи старую папку «Кандидаты» в `GOOGLE_DRIVE_ROOT_FOLDER_ID` и выполни `npm run drive:auth` аккаунтом, которому она принадлежит, — тогда у приложения будет доступ ко всем импортированным резюме.
2. В Google Sheets: `Файл -> Скачать -> Microsoft Excel (.xlsx)`.
3. Накати схему на **пустую** базу:

   ```bash
   npm run migrate
   ```

4. Запусти импорт:

   ```bash
   npm run import:sheets -- ./recruiting-ats.xlsx
   ```

Особенности:

- импорт выполняется только в пустую базу (без кандидатов) и одной транзакцией: при любой ошибке ничего не записывается;
- переносятся листы `Пользователи`, `Вакансии`, `Источники`, `Ответственные`, `Шаблоны интервью`, `Кандидаты`, `Архив кандидатов`, `Интервью`, `Candidate Transition Status Log`, `Справочники`; отсутствующие листы пропускаются с предупреждением;
- исходные ID и номера (`№`) сохраняются (невалидные и дубли заменяются новыми), последовательности синхронизируются;
- файлы **не копируются**: резюме и папки кандидатов уже лежат в Google Drive, импортируются их Drive ID — ID файлов резюме (из `id` в «Версиях резюме», `Resume File ID` или URL) в `files.drive_file_id` и ID папок (из URL «Папки кандидата») в `candidates.drive_folder_id`. Поэтому старые резюме продолжают открываться через ATS, а новые резюме импортированных кандидатов попадают в их существующие папки;
- записи без Drive ID сохраняются как внешние ссылки (`files.external_url`);
- для старых записей без обязательных связей создаются архивные заглушки: пользователь «Импорт Не назначен» и вакансия «Без вакансии (импорт)».

- ответственные становятся пользователями (с этапами), комментарии кандидатов и вакансий переносятся в ленту комментариев от имени «Перенесено из старой версии», ответы и результаты интервью — в HTML; удалённые записи попадают в корзину.

> Выгрузка `.xlsx` содержит персональные данные кандидатов. Не коммить её и удали после импорта.

## Схема БД

Схема описана в `server/db/migrations/001_init.sql` и последующих миграциях (`002_*` … `006_app_settings.sql`). Применённые миграции учитываются в таблице `schema_migrations`.

| Таблица | Назначение |
|---|---|
| `users` | Пользователи ATS (они же ответственные): Google `sub`, email, `last_name` / `first_name` / `middle_name`, аватар, `is_active`, `is_admin`, этапы ответственного `stages` (непустой список = ответственный), последний вход, `archived_at` / `deleted_at`, Telegram (`telegram_username`; `telegram_chat_id` — только у подтверждённых; одноразовый код привязки). |
| `vacancies` | Вакансии со статусом `Открыта` / `На паузе` / `Закрыта`, обязательные этапы `required_stages` (при переходе нужен итог), `archived_at` / `deleted_at`. |
| `sources` | Источники кандидатов. Название уникально среди неудалённых. |
| `interview_templates` | Шаблоны вопросов; к вакансии привязываются по этапам через `vacancy_templates` (не больше одного шаблона на этап, `required` совпадает с обязательностью этапа). |
| `files` | Метаданные файлов: ID файла в Google Drive (`drive_file_id`) или внешняя ссылка (`external_url`) для импортированных резюме без Drive ID. |
| `candidates` | Кандидаты: контакты, вакансия, статус, назначения (рекрутер, HR, проф. интервьювер — ссылки на `users`), ссылки, папка в Google Drive (`drive_folder_id`), `archived_at` / `deleted_at`. |
| `candidate_resumes` | Версии резюме кандидата (связь `candidates` ↔ `files`). |
| `interviews` | Результаты интервью/этапов: ответы на вопросы шаблона и итог (HTML), ответственный (`users`). |
| `comments` | Комментарии к кандидатам, вакансиям и результатам интервью (`entity_type` + `entity_id`): автор, текст в HTML (`body_html`), `parent_id` для ответов, время правки. |
| `comment_reactions` | Реакции на комментарии: комментарий + пользователь + эмодзи. |
| `app_settings` | Настройки интеграций из интерфейса (ключ → значение, секреты зашифрованы), кто и когда менял. |
| `candidate_watchers` | Подписки «Следить» на кандидатов. |
| `notification_preferences` | Настройки уведомлений пользователя: вид × канал → включено. Нет строки — значение по умолчанию. |
| `notifications` | Уведомления: получатель, вид, кандидат, автор, заголовок и текст, `in_app` (показывать в колокольчике), `important`, `read_at`. |
| `notification_deliveries` | Доставка по email и Telegram: статус (`pending` / `sent` / `failed` / `skipped`), адресат, число попыток, ошибка, время следующей попытки. |
| `candidate_status_log` | Append-only журнал переходов статусов (текст без разметки). UPDATE и DELETE запрещены триггером, кроме окончательного удаления кандидата из корзины. |
| `candidate_drafts` | Черновики кандидатов из Resume Intake API: токен, данные, резюме, срок действия (7 дней). |
| `dictionaries` | Справочники (статусы кандидата, статусы вакансии и т.п.). |
| `session` | Сессии пользователей (connect-pg-simple). |
| `schema_migrations` | Учёт применённых миграций. |

Общие принципы:

- первичные ключи — UUID; человекочитаемые номера `№` берутся из identity-последовательностей;
- у кандидатов, вакансий, источников, шаблонов, результатов интервью и пользователей есть `archived_at` (архив) и `deleted_at` (корзина); в корзину попадает только архивная запись (CHECK-ограничение), через 30 дней в корзине запись удаляется из БД окончательно, зависимые записи удаляются каскадом или отвязываются (`ON DELETE CASCADE` / `SET NULL`);
- многострочные поля хранят очищенный HTML (см. [Форматированный текст](#форматированный-текст));
- новые миграции добавляются файлами `server/db/migrations/NNN_*.sql` и применяются по порядку имени.

### Файлы в Google Drive

Структура та же, что в прежней версии на Apps Script:

```text
<GOOGLE_DRIVE_ROOT_FOLDER_ID> («Кандидаты»)
  <ФИО> - <первые 8 hex ID кандидата, в верхнем регистре>/
    yyyy-MM-dd-HH-mm-ss - <исходное имя файла>
  _ATS_Черновики/
    <первые 8 символов токена> - <имя файла>
```

- Папка кандидата создаётся при первой загрузке резюме; если её удалили или переместили в корзину, она создаётся заново.
- Резюме черновика из Resume Intake API лежит в `_ATS_Черновики` и копируется в папку кандидата при сохранении кандидата.
- Если сохранение не удалось, файлы и папки, созданные этим запросом, переносятся в корзину Drive.
- `npm run cleanup-drafts` переносит файлы черновиков в корзину Drive (не удаляет безвозвратно).
- При окончательном удалении кандидата из корзины ATS его папка переносится в корзину Drive.

Ссылка `/files/:id` доступна только авторизованным пользователям: сервер читает файл из Drive и отдаёт его потоком, поэтому пользователям ATS не нужны собственные права в Drive. PDF открывается в браузере, DOC/DOCX скачиваются. Нативные документы Google (Docs и т.п.) открываются редиректом на их `webViewLink`.

«Папка кандидата» — страница `/candidates/:id/files` со всеми версиями резюме и ссылкой «Открыть папку в Google Drive» (для неё уже нужен доступ к папке в Drive).

## Resume Intake API

Для интеграции с AI/ChatGPT сервер предоставляет `/intake`: получение справочников и создание предзаполненных черновиков кандидатов. API не создаёт кандидата без подтверждения пользователя: он возвращает ссылку `PUBLIC_URL/?draft=<token>`, по которой открывается заполненная форма.

- Документация: [`docs/API.md`](docs/API.md)
- Skill: `skills/recruiting-ats-resume/SKILL.md`
- OpenAPI: `skills/recruiting-ats-resume/openapi.yaml` (замени `servers.url` на свой `PUBLIC_URL`)

## MCP-сервер и плагин Claude

`{PUBLIC_URL}/mcp` — MCP-сервер, через который Claude (Claude Code, Claude Desktop) ищет кандидатов, читает резюме, заводит черновики, переводит по этапам, комментирует и строит отчёты — от имени пользователя и с его правами. Подключение — кнопкой «Connect» / «Authenticate» в клиенте (вход в ATS и страница «Разрешить доступ», OAuth 2.1 + PKCE) или личным токеном из профиля (переменная `ATS_MCP_TOKEN` для плагина), если прокси не пропускает `/.well-known/*`. Подключения видны и отключаются в «Профиль → Claude и AI-ассистенты».

Плагин Claude Code — `plugins/recruiting-ats` (MCP-сервер, скилл с правилами превью и подтверждения, скиллы собеседований — шаблоны вопросов по этапам, HR-скрининг, техническое интервью .NET, оформление результатов — и команды `/recruiting-ats:*`):

```text
/plugin marketplace add totKtoXam/recruting_ats
/plugin install recruiting-ats@recruiting-ats
/mcp   → recruiting-ats → Authenticate
```

Адрес по умолчанию — `https://portal.devexpert.kz/hr-ats/mcp`; другой — переменная окружения `ATS_MCP_URL`. Протокол, инструменты и загрузка резюме описаны в [`docs/API.md`](docs/API.md#mcp-сервер-для-claude).

## Безопасность

В GitHub не должны попадать:

- `.env` и любые файлы с секретами (`SESSION_SECRET`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_DRIVE_REFRESH_TOKEN`, `GOOGLE_DRIVE_SERVICE_ACCOUNT_KEY` и файлы ключей сервисного аккаунта, `ATS_API_KEY`, пароли БД);
- выгрузки `.xlsx` из Google Sheets и любые другие персональные данные кандидатов.

Что сделано в приложении:

- все страницы, RPC и файлы доступны только после входа; сессия хранится в PostgreSQL, cookie `ats.sid` — `HttpOnly`, `SameSite=Lax`, `Secure` в production;
- RPC принимает только `application/json`, поэтому простые кросс-сайтовые формы не пройдут без CORS preflight;
- OAuth защищён параметром `state`, после входа сессия пересоздаётся; редирект после входа — только на относительные пути приложения;
- файлы из Google Drive отдаются только авторизованным пользователям через сервер; публичные ссылки на файлы в Drive не создаются;
- форматированный текст (комментарии, ответы интервью и т.п.) очищается на сервере через `sanitize-html` по белому списку тегов и схем ссылок — защита от XSS;
- удаление в корзину, восстановление и управление пользователями доступны только администраторам (проверяется на сервере);
- формат (PDF/DOC/DOCX) и размер (до 10 МБ) резюме проверяются на сервере;
- API key Resume Intake API сравнивается за постоянное время;
- `AUTH_MODE=dev` запрещён в production.

Рекомендации:

- ограничивай доступ через `AUTH_ALLOWED_DOMAINS` / `AUTH_ALLOWED_EMAILS` и тип `Internal` экрана согласия Google;
- передавай `ATS_API_KEY` в заголовке `X-API-Key`, а не в query: query-строки попадают в логи прокси;
- периодически меняй `ATS_API_KEY`; смена `SESSION_SECRET` разлогинит всех пользователей;
- `DATABASE_SSL=true` включает TLS без проверки сертификата сервера — для недоверенных сетей используй приватную сеть до БД;
- `GOOGLE_DRIVE_REFRESH_TOKEN` и ключ сервисного аккаунта — секреты с полным доступом к Google Drive соответствующего аккаунта (scope `drive`): храни их только в секретах окружения и никогда не коммить;
- заведи для ATS отдельный Google-аккаунт, которому принадлежит папка «Кандидаты», а не используй личный: при утечке токена под угрозой только файлы ATS;
- настрой резервное копирование PostgreSQL: записи из корзины ATS через 30 дней удаляются из БД безвозвратно; резюме в Google Drive удаляются только в корзину Drive, но папку «Кандидаты» тоже стоит периодически выгружать (например, через Google Takeout).
